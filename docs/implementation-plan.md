# Digital Heroes implementation plan

The submission is an operational print workflow for six divisions. The HR brief defines the deliverables and evaluation. The build PRD supplies the demo price values, rules for resolving proof and payment races, fixture sizes, and acceptance examples. New quotes use INR with the existing numeric fixture values and a 20% demo tax rate. Shop collection and RGB print profiles also use demo settings. The HR phrase “score / configuration” is satisfied with the saved configuration because the brief gives no scoring model.

## Architecture

- **Web and API.** Next.js App Router and React serve the storefront, designer and operations console. Business rules live in TypeScript modules independent of UI. API handlers validate identity, ownership, and request bodies. The form calculates quotes immediately using shared logic. The API independently calculates and records the authoritative quote. [Next.js Route Handlers](https://nextjs.org/docs/app/getting-started/route-handlers)
- **Persistence and identity.** Use PostgreSQL migrations on Supabase and Supabase Auth in the hosted environment. Use a private database schema for server writes. The local demo runs the PostgreSQL schema through PGlite with local sessions, a loopback-bound payment simulation, and private files on disk. Run joint acceptance against real Postgres before claiming cross-process concurrency. Use the transaction pooler for serverless connections. [Supabase server-side auth](https://supabase.com/docs/guides/auth/server-side/nextjs) · [Supabase connection modes](https://supabase.com/docs/guides/database/connecting-to-postgres) · [PGlite](https://pglite.dev/docs/)
- **Print fidelity.** Keep geometry in millimetres. Pin the renderer and font assets in the release and stamp their version on each proof. Render proofs and production from the same geometry, glyph placement and snapshot. The initial RGB pipeline embeds the 300 ppi bitmap in a PDF with explicit media, bleed and trim boxes. Operator-approved colour profiles, vector cut paths and equipment validation are separate production decisions. [PDF page boxes](https://pdf-lib.js.org/docs/api/classes/pdfpage#settrimbox)
- **Untrusted uploads.** Obtain a short-lived signed upload for a private staging key on the hosted path, then verify bytes and convert to a safe normalised image. Cap input bytes, pixel count, pages, render time and worker memory. Validate dimensions and actual type. Accept single-artboard PDF-compatible AI with a re-export message for other AI files. The 25 MB requirement exceeds Vercel's default request limit and its 20 MiB beta option. [Vercel request limit](https://vercel.com/docs/errors/function_payload_too_large) · [Supabase Storage access control](https://supabase.com/docs/guides/storage/security/access-control) · [Illustrator PDF compatibility](https://helpx.adobe.com/illustrator/desktop/save-and-export/export-files-to-different-formats/save-artwork-in-illustrator-ai-format.html)
- **Settlement and generation.** Link a checkout attempt to the current approved proof and exact financial snapshot. Validate signed Stripe events with the raw body. Lock the order row while checking the binding and recording payment, enqueueing a unique job and writing an audit event in one transaction. Record obsolete or mismatched money for review. Provider events can arrive more than once. [Stripe fulfillment](https://docs.stripe.com/checkout/fulfillment.md?ui=full-page) · [Stripe webhook signature verification](https://docs.stripe.com/webhooks/signature)
- **Recoverability.** Workers claim rows with `FOR UPDATE SKIP LOCKED`, use expiring leases and write into attempt-specific storage keys. Only the current lease can publish a complete manifest. Readers see the manifest after it commits. Staff can retry a failed job using the same approval and payment. Use separate execution capacity for rendering so a stopped browser or web request does not stop the print queue. [PostgreSQL locking clause](https://www.postgresql.org/docs/current/sql-select.html#SQL-FOR-UPDATE-SHARE)

## Data boundaries

`accounts → orders → proofs` holds access and artwork history. Each proof contains the approved configuration, print profile, resolved design and row data. `catalogue` holds editable configuration and prices. Changes to it apply to new quotes. `checkout_attempts → payment_event_log → payments` tracks the gateway handshake and confirmed money. `jobs → manifest` tracks rendering and published files. `order_events` holds actor and timestamp for stage changes, proof decisions and payment exceptions. The schema reference accompanies migrations.

A quote becomes an order after sign-in and price confirmation. Draft changes return the job to Artwork. Publication advances it to Proof. Approval enables checkout. Payment and file generation are independent states while the order is in Proof. Staff start Production only after the current approved paid version has a complete manifest, then mark it Completed. Completed records are archived in place and can be used as the source of a new order.

## Verification before handover

- Verify exact integer-minor-unit rounding, both quantity thresholds, invalid dimensions, and stale quote rejection.
- Test count mismatch, duplicate bibs, UTF-8 and leading zeros, unsupported glyphs, fit failures, approval from an old tab and post-payment edit rejection.
- Test customer isolation on order, proof, receipt and storage routes. Verify staff can download only a ready paid approval. Exercise replay, mismatched amount and superseded checkout events through the same settlement logic.
- Interrupt or fail a render, retry and confirm a single complete manifest. Inspect actual PDF page boxes, PNG resolution metadata and a visual comparison against the customer's row proof.
- Check touch and keyboard interactions at 360 px and desktop at 1440 px. Keep the final acceptance record tied to the deployed URL and reviewer accounts.
